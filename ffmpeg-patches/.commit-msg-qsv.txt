fix(qsv): make dense ROI maps frame-owned and contract-bounded

Stock qsvenc maps AV_FRAME_DATA_REGIONS_OF_INTEREST onto
mfxExtEncoderROI rectangles. Pelorus's progressive HEVC+CQP path on QSV
runtime API 1.28 or newer instead rasterizes the same side data into a dense
mfxExtMBQP DeltaQP array.

The previous patch kept that array as mutable QSVEncContext scratch while each
per-frame mfxExtMBQP header pointed at it. EncodeFrameAsync can retain several
QSVFrame controls at once, so submitting frame N+1 repainted frame N's map
before frame N's surface unlocked.

Allocate one zeroed block per ROI-bearing frame: the mfxExtMBQP header followed
immediately by its DeltaQP array. Attach the header to that frame's existing
mfxEncodeCtrl so free_encoder_ctrl releases the entire allocation after the
surface unlocks. Frames no longer share mutable map storage.

Bound the dense contract to progressive HEVC+CQP on runtime API 1.28 or newer,
where FFmpeg attaches mfxExtCodingOption3. H.264, non-CQP HEVC, interlaced
input, older runtimes, and builds without the API-1.13 MBQP headers fall back to
stock mfxExtEncoderROI with accurate diagnostics. Dense selection inspects the
final attached CodingOption3 after init/reset and caches whether EnableMBQP=ON
after any AVQSVContext same-BufferId replacement; the dense and rectangle
buffers are never attached together.

Build the 16x16 raster from aligned mfxFrameInfo storage dimensions, clip ROI
coordinates to the visible frame, leave padding cells zero, validate every ROI
entry, and check cell-count/allocation arithmetic plus oneVPL field narrowings.

Verified against the configured FFmpeg n9.0.2 commit with the direct ASan/UBSan
regression (two live maps, aligned padding, overlap precedence, malformed input,
interlaced choice) and QSV TU builds with QSV_HAVE_MBQP both enabled and forced
disabled. A hostile-hook run left no owned worktree or scratch residue. Hardware
async execution remains pending; no runtime support or quality result is
inferred from compile/harness evidence.
