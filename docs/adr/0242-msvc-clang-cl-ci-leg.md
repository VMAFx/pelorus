# ADR-0242: Build and test libpelorus with cl.exe and clang-cl in CI

- **Status**: Accepted
- **Date**: 2026-11-03
- **Deciders**: Lusoris
- **Tags**: ci, windows, build, testing

## Context

The only Windows compiler in CI is MinGW-w64 GCC in the MSYS2 UCRT64 `windows` job ([ADR-0149](0149-windows-utf8-paths.md)). Two fixes target the MSVC-ABI compilers: 4aae307 opens the qp-report CSV with `_wfsopen` so cl.exe reports no C4996 (#88), and 11e183e reads the interop fixtures back with `_fsopen` so clang-cl and icx-cl report no `-Wdeprecated-declarations` (#90). No CI job runs either compiler, so nothing keeps those fixes in place, and `libpelorus/test/meson.build` names MSVC as a supported toolchain without a leg that proves it. The gap audit of 2026-10-12 recorded both points (rows C11-02 and C13-09, issue #455).

libpelorus marks no symbol `__declspec(dllexport)`. GCC on Windows exports every symbol of a DLL by default; cl.exe and clang-cl export none, so a shared libpelorus built with them has no import library and the tests cannot link.

## Decision

A `windows-msvc` job in `.github/workflows/ci.yml` runs on the pinned `windows-2025` image with a matrix of `cl` and `clang-cl`:

- Meson and Ninja come from PyPI, pinned with hashes in `.config/msvc-ci/requirements.txt` (generated by `uv pip compile --generate-hashes` from `requirements.in`).
- `meson setup --vsenv --werror build -Ddefault_library=static -Dshaders=false` loads the Visual Studio environment. With `warning_level=3`, cl.exe compiles at `/W4 /WX`, and clang-cl takes the same flags.
- The job reads the compiler line from `meson-log.txt` and fails unless Meson chose the compiler the matrix asked for, so a fallback to another compiler on `PATH` cannot pass.
- It runs the fast suite and requires the `sei-fit` tests and `path-utf8` to have run, not skipped.

The library is static in this leg. A shared MSVC build needs export annotations or a module-definition file; that is a feature of its own, not a warning fix. The reference shaders stay in the Linux and MSYS2 jobs, which install glslang.

`scripts/check-build-config.py` validates the job: runner, matrix, `--werror`, the compiler assertion, the hashed install, the fast suite and digest-pinned actions. Its `--self-test` plants eight defects, one per rule, each of which must be refused.

The matrix uses the `include` form so the Praetor engine expands one check context per compiler. The committed ruleset `.github/rulesets/main.json` lists both, `libpelorus (Windows · cl · fast suite)` and `libpelorus (Windows · clang-cl · fast suite)`, in job-id order (16 checks), as [ADR-0239](0239-semgrep-float-identity-rule.md) did for the `semgrep` job; the maintainer applies the live ruleset with `praetorctl sync --remote` after this change lands.

## Alternatives considered

| Option | Result | Why not chosen |
| --- | --- | --- |
| cl.exe and clang-cl matrix (chosen) | Covers both compilers named by #88 and #90 on the stock runner image | Two runner jobs per pull request |
| clang-cl only | One job | cl.exe C4996 (#88) stays unchecked |
| Add icx-cl as a third leg | Covers the third compiler named by #90 | The Intel oneAPI compiler is not on the runner image; installing it adds several minutes and a download outside the pinned toolchain set per run |
| Cross-compile with clang-cl from Linux against a downloaded Windows SDK (xwin) | Linux runners only | Requires accepting the Microsoft SDK licence in CI and does not run the tests on Windows |
| Shared library with a `.def` file | Proves the DLL the MinGW leg ships | Separate feature; the warning gap is closed without it |

## Consequences

- A change that adds a cl.exe or clang-cl warning fails CI on pull requests, the same way GCC and Clang warnings already do.
- The MSVC-ABI build is static only until libpelorus gains export annotations.
- The first run found two defects the MinGW leg could not see, both fixed with this change: `encode_options.c` included the POSIX `<strings.h>` for `strcasecmp`, which MSVC does not ship (an ASCII-only `ascii_ieq` replaces it and also drops locale-dependent folding), and cl.exe reported C4701 (potentially uninitialized) for a `TlmSpan` local in `telemetry_adapters.c` that is only read after a successful parse; every `TlmSpan` local now starts as `{NULL, 0}`.
- The compile step passes `-k 0` to Ninja, so one run reports every failing unit rather than the first.
- icx-cl remains outside CI; issue #90's fix is covered through clang-cl, which reports the same `-Wdeprecated-declarations` diagnostic.
